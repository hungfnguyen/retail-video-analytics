### 1.7 Chốt semantics idempotency cho Gold serving refresh

Đã sửa tại:

- `services/flink-jobs/java/src/main/java/org/rva/gold/GoldServingBatchJob.java`
- `services/flink-jobs/python/submit_batch_job.py`

Thay đổi:

- toàn bộ batch step Gold serving đổi từ:
  - `INSERT OVERWRITE ...`
  thành:
  - `INSERT INTO ...`
- submitter giờ chủ động:
  1. lấy batch lock
  2. `DELETE` đúng `metric_date` window trên target table bằng Trino
  3. submit Flink batch job để `INSERT INTO`
  4. poll `jobId` đến khi `FINISHED/FAILED`
  5. ghi audit

Ý nghĩa:

- semantics refresh rõ ràng và dễ hiểu hơn `INSERT OVERWRITE` trong Flink/Iceberg
- rerun cùng `domain + date window` không nhân đôi dữ liệu
- logic idempotency nằm ở orchestration layer, đúng với vai trò Airflow/submitter

Trade-off đã chấp nhận:

- nếu fail sau bước `DELETE` nhưng trước khi `INSERT` hoàn tất, partition/window đó có thể tạm
  thời rỗng cho đến lần retry kế tiếp
- với scope local/demo hiện tại, trade-off này chấp nhận được và dễ quan sát qua audit hơn việc
  phụ thuộc semantics overwrite của connector

- **nhưng** vẫn còn một run `gold_serving_queue_hourly` `FAILED` (start 19:44, tức là run mới sau rebuild)

Root exception (nested cause):

```text
java.io.IOException: Insufficient number of network buffers:
required 512, but only 441 available.
The total number of network buffers is currently set to 5079 of 32768 bytes each.
```

### 6.2 Root cause: per-domain parallelism mâu thuẫn với cluster config

- `infrastructure/flink/conf/flink-conf.yaml` đã chốt `parallelism.default: 1` cho batch,
  kèm comment giải thích đúng lý do: shared local cluster + streaming luôn chạy giữ phần lớn
  network buffer pool, nên batch shuffle với parallelism > 1 sẽ vỡ network buffers.
- Nhưng patch 1.12 (`configureBatchParallelism`) lại **ghi đè ngược** lên config đó bằng
  `table.exec.resource.default-parallelism = 2..4` theo domain, tái tạo đúng áp lực buffer mà
  flink-conf muốn tránh. `queue_hourly` (p=2) cần 512 buffers nhưng pool chỉ còn 441 trống.

Đã sửa tại:

- `configureBatchParallelism` giờ **tôn trọng** `parallelism.default` (=1) của cluster:

## 8. CHỈNH SỬA QUAN TRỌNG — Flink bỏ qua `'partitioning'`; chuyển sang `PARTITIONED BY` (verify runtime)

> Phần 7 ở trên mô tả cách sửa qua thuộc tính `'partitioning'` trong Flink `CREATE TABLE ... WITH (...)`.
> Khi verify runtime sau rebuild, phát hiện cách đó **không hoạt động**. Mục 8 là cách triển khai
> đúng cuối cùng, **thay thế** chi tiết kỹ thuật ở 7.1/7.2.

### 8.1 Bằng chứng runtime

- Drop 2 bảng heatmap -> DAG Flink tạo lại bằng JAR mới (có `'partitioning'='metric_date,store_id,bucket(16,camera_id)'`)
  nhưng bảng ra **không có partition** (`"<table>$partitions"` không có cột `partition`).
- `silver_detections_v2`, `gold_track_summary_v2` cũng **unpartitioned** ở runtime dù code có
  `'partitioning'` WITH.

➡️ Kết luận: **Flink Iceberg connector bỏ qua thuộc tính `'partitioning'` trong WITH.** Partition
của gold_serving cũ thực ra do **Trino DDL** `services/gold_serving/sql/ddl/gold_serving.sql`
(`partitioning = ARRAY[...]`, apply qua `apply_ddl.py`) tạo ra — Trino honor, Flink thì không.
(Đã lưu memory `flink-ignores-partitioning-property`.)

### 8.2 Test cú pháp `PARTITIONED BY` trên Flink SQL client (Flink 1.18 / Iceberg 1.5)

- `PARTITIONED BY (metric_date, store_id)` (identity) -> **OK**, `$partitions` có cột `partition`.
- `PARTITIONED BY (metric_date, store_id, bucket(16, camera_id))` (transform) -> **FAIL parse**
  (`Encountered "(" ...`). Flink SQL parser **không** nhận transform function trong `PARTITIONED BY`.

### 8.3 Quyết định triển khai (đã chốt với người dùng: dùng Flink `PARTITIONED BY`)

- Vì Flink không làm được `bucket(...)`, heatmap dùng **identity `camera_id`** thay vì
  `bucket(16, camera_id)`. Với demo ít camera, identity prune chính xác hơn và chạy native trên Flink.
- Partition cuối cùng (đồng bộ ở **cả 2** DDL để hết race):

| Bảng | Partition |
|---|---|
| traffic/queue/zone/dwell/alert hourly+daily, `executive_daily` | `metric_date, store_id` |
| `heatmap_tile_5min` / `heatmap_tile_hour` | `metric_date, store_id, camera_id` |
| `refresh_audit` / `data_quality_results` | `partition_date` |

Đã sửa:

- `services/flink-jobs/java/src/main/java/org/rva/gold/GoldServingSupport.java`
  — toàn bộ DDL đổi từ `WITH ('partitioning'=...)` sang mệnh đề `PARTITIONED BY (...)`.
- `services/gold_serving/sql/ddl/gold_serving.sql`
  — `partitioning = ARRAY[...]` đồng bộ đúng spec trên (Trino honor). Giờ **cả 2 DDL tạo ra cùng
  partition**, nên dù Flink `ensureServingTables` hay Trino `apply_ddl` chạy trước sau drop thì
  bảng vẫn partition đúng (hết race "tạo nhầm bảng unpartitioned").

`mvn -q -DskipTests package` pass.
